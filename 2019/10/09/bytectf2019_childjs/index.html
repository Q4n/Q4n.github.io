本题思路

基于CVE 2019-0567 / CVE 2019-0539, 是chakra的一个类型混淆漏洞

在CVE-2019-0539 PoC中，对象o以（#3）形式的内存布局开始其生命周期。然后，当JIT代码最后一次调用OP_InitClass函数时，对象o的内存布局就变更为（#1）。但是, 之后jit对其的操作仍然当做是(#3)来处理的

这里的混淆是(#1)和(#3)这两种布局被混淆了, 那么假如我们把#1类型布局的对象o当做#3来写, 那么我们可以控制auxSlots指向另外的一个obj, 然后接着, 我们对o进行操作的时候, 因为他实际的布局是#1, 所以他会去写auxSlots指向的区域, 但是此时我们已经让他指向了obj, 所以实际上我们就可以控制对象obj的任意一个属性

经过JIT优化编译后，Chakra引擎会移除检查对象类型是否一致的代码。攻击者可以通过旧类型的操作访问新类型对象内存区域以外的数据，实现内存越界读写。

预期的布局方式

构造R/W原语的思路:
利用两个DataView对象, 因为DataView对象中有直接指向缓冲区的指针, 所以利用这两个对象的setInt32(offset,data,true)和getInt32(offset,data,true)两个方法就可以实现任意地址读写

这里有一点注意, 比如说新建一个 DataView 对象 dv1, 那么这个dv1指向的地址就是这个对象的头部, 即vtable的区域

getshell的思路:

在执行 JavaScript 语句Uint8Array.set(Uint8Array)时，Chakra引擎会调用glibc库的memmove函数。我们可以将libChakraCore.so GOT 表上memmove函数地址修改为system，然后将 Shell 命令作为参数传给Uint8Array.set(Uint8Array)语句，实现任意命令执行。
